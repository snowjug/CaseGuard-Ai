# Performance benchmark

> Generated by `pnpm bench:api` (`scripts/bench-api.ts`). Do not edit by hand: re-run the command. The numbers below are exactly what that run measured.

**What this is.** A micro-benchmark of one local API process: the API is built in the benchmark process (`buildApp`), requests are injected without a network, the database is an in-memory PGlite seeded with the synthetic demo story, and the AI provider is the deterministic offline engine (no model call). Every request goes through the real pipeline (authentication, permission check, validation, handler, response validation, audit). **What this is not.** It is not a load test (one request at a time), not a capacity plan and not a comparison with any other system, and no service-level objective is claimed. Case ingestion is measured without starting its analysis. The page-render timing of the Case Timeline in a browser is measured separately by the on-demand Playwright spec `e2e/perf/timeline-render.spec.ts`.

## Reading the table

- **Timeline, whole record** serves the stored analysis. **Earlier instants** are recomputed by the engine on a temporal view that holds only what was recorded by then (never a filtered copy of the final analysis); the first request for a window is _cold_, a repeat is _warm_ and comes from the cache.
- **Counterfactual job initiation** is the time until the API answers `202` with a job; the job itself runs afterwards on the same process, and its duration is listed separately for reference. Each iteration runs the next decision fork of Case One in turn, so after the first round a fork is asked for again; the engine keeps its recent replays in a cache, so a repeat can be cheaper than the first request for a fork, and the job durations are not one population.
- Each run measures its own process from a cold start, so the first requests of a row may include one-time costs; that is what the warm-up requests are for.
